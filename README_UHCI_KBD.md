## ЭТАП 2 — «порты 2.0»: что ещё было сломано на реальном железе

Обратная связь с реальной машины (AMD FCH: 2×xHCI + 2×EHCI +
2×OHCI-компаньона): **в 3.0 работает всё, включая переподключение;
в 2.0 не работает НИЧЕГО** — ни клавиатура, ни мышь, по отдельности
и вместе. Четыре корневые причины найдены и исправлены:

1. **DATA-стадия контрольной передачи шла с тогглом DATA0** (спека
   USB: SETUP=DATA0 → DATA=DATA1 → STATUS=DATA1). Реальное устройство
   отвечает DATA1 — тоггл не сходится, дескрипторы отклоняются,
   перечисление умирает на первом GET_DESCRIPTOR. **QEMU тогглы
   контрольных труб не проверяет — поэтому все e2e проходили, а
   железо молчало.** Теперь DATA-qTD несёт QTD_DT (бит 31 токена).
   Это и была «мёртвая клавиатура в порту 2.0».
2. **Выравнивание qH — 32 байта, не 16**: у EHCI указатели несут
   только биты 31:5. При мульти-инстансе (2×EHCI!) строка массива
   была 48 байт — второй qH попадал на 16-байтовую границу,
   контроллер обрезал ссылку 0x…9f2 → 0x…9e0 и читал «qH» из хвоста
   ПЕРВОГО инстанса. Порты, висящие на ВТОРОМ EHCI, не работали
   ВООБЩЕ (видно в трассе QEMU: `usb_ehci_qh_ptrs: QH @ 0x…9e0:
   next 0`). Строки eh_head/eh_qhc расширены до 64 байт — этот класс
   бага уже ловили в 0.3.2 на g_qhi, теперь закрыт и для инстансов.
3. **ОДНО расписание на ДВА контроллера**: mmio-указатель, async-
   кольцо, периодическая таблица и слоты устройств были общими —
   инициализация второго EHCI затирала расписание работающего
   первого. Теперь всё состояние ПЕР-ИНСТАНСНОЕ (массивы _a[2],
   селектор g_ei), зондируются ОБА контроллера (AMD: 0:12.2 и 0:13.2).
4. **CONFIGFLAG «машел» портами туда-сюда**: mouse_hw_init зондировал
   OHCI-компаньонов ДО ehci_init, а тот ставил CONFIGFLAG=1 и отбирал
   порты обратно — уже перечисленная мышь срывалась. Теперь порядок
   `mouse_hw_init (xHCI) → ehci_init → mouse_hw_init_ohci (компаньоны
   зондятся ПОСЛЕ раздачи им LS/FS-портов навсегда) → UHCI`.

Дополнительно: ретраи неперечисленных портов (до 3 попыток в
секундном опросе, честный бэкофф — сброс порта сам поднимает CSC,
счётчик больше не обнуляется собственным ресетом), PED-порты BIOS
сбрасываются перед перечислением, handoff EHCI глушит USBLEGCTLSTS
(SMI-источники), OHCI при молчании SMM забирает владение силой
(HcControl.IR=0), чтение DMA-памяти — через volatile (GCC -O2
выносил токены qTD из цикла ожидания), перестройка периодической
цепочки — под выключенным PSE.

## 0.3.0 — «хочу любые комбинации портов, опрос каждую секунду и реестр»

Запрос пользователя: *«клавиатура в 2.0 и мышь 2.0, или обе в 3.0, или
клавиатура в 3.0 а мышь 2.0… опрашивай все порты каждую секунду,
переподключения, каждый драйвер пробуй к устройству, не подошло ни
один — пиши неизвестное устройство»*.

### Новое ядро модели — `kernel/usbdev.c` (диспетчер)

* **ШЕСТЬ драйверов**: клавиатура 1.x / 2.0 / 3.0 и мышь 1.x / 2.0 / 3.0.
* ОС **спрашивает у порта** «кто ты?» — порт отвечает версией:
  xHCI → «USB 3.0», EHCI → «USB 2.0», UHCI/OHCI → «USB 2.0», если на
  машине есть EHCI (порт 2.0 отдан компаньону), иначе «USB 1.x».
* Новое устройство → **сначала «драйвер клавиатуры <версия>»**; если
  подошёл — записывается в реестр и **больше не подбирается ни к кому**.
  Занят/не подошло → «драйвер мыши <версия>». Не подошёл и он —
  **«НЕИЗВЕСТНОЕ УСТРОЙСТВО»** (флешка, вторая клавиатура и т.п.).
* **`usbdev_tick()` — каждую секунду** (RTC), **независимо от
  обстоятельств**, обходит **ВСЕ порты ВСЕХ контроллеров**: xHCI×2 +
  OHCI×2 (инстансы!) + EHCI + UHCI (мышь и клавиатура).
* Выдёргивание устройства → слот реестра освобождается → следующий
  претендент занимает его при следующем опросе.

### Мульти-инстансы контроллеров (AMD FCH: 2×xHCI + 2×OHCI)

Раньше вся DMA-память xHCI была общей: зонд второго контроллера
затирал буферы первого — «мышь+клава оба в 3.0» ломались, если
доставались разным контроллерам. Теперь у каждого инстанса свои
DCBAA/кольца/контексты/scratchpad; опрашиваются оба. OHCI — так же
(оба компаньона живут одновременно: клава на 0:12.0, мышь на 0:13.0).

### Исправленные корневые баги

1. **Переподключение мыши не работало ВООБЩЕ**: `um_deactivate()` не
   сбрасывал `g_present` → `usb_mouse_rescan()` навсегда пропускала
   контроллер («наш, пусть и на паузе»). Теперь сбрасывает, и мышь,
   воткнутая обратно, поднимается за секунду.
2. **«Клава видится, а клавиши не работают» на xHCI** (баг с 0.3.1):
   EP-контекст клавиатуры писался в input-контексте по смещению
   `32*epid` вместо `32 + 32*epid` (спека 6.2.5). Контроллер читал
   нули → ring->dequeue=0 → отчёты никогда не приходили. Исправлено.
3. **Коллизия адреса 0 на UHCI**: неадресованное устройство в соседнем
   порту слышало те же addr-0 транзакции — перечисление второго
   устройства читало дескрипторы ПЕРВОГО. Теперь сосед приглушается, а
   каждому перечислению выдаётся уникальный адрес (2 — клавиатура).
4. **ERSTBA-выравнивание**: ERSTBA маскируется до границы 64 байта —
   второй инстанс с 32-байтовым шагом массива терял события.
5. **Уступка контроллера**: мышь, воткнутая в контроллер живой
   UHCI-клавиатуры, теперь поднимается: клава отвязывается, мышь
   привязывается первой, клава возвращается в общем расписании
   (shared-режим) — всё за один секундный опрос.
6. **SMM/BIOS не отдавал OHCI (фото с реального железа!)**: HCR-сброс
   НЕ останавливает SMM-обработчик «USB Legacy Support» — BIOS
   продолжал поллить OHCI и затирал наши ED/TD («СМАЗ: control ED
   word0 = 0x1000, MPS=0»), каждый SET_ADDRESS получал cc=5
   DeviceNotResponding, low-speed устройство «отвечало» нулями
   (фейк-OK). QEMU этого не эмулирует — там всё проходило. Теперь
   `probe_ohci()` делает правильный handshake по спеке OHCI 5.1.1.3
   (как Linux ohci-hcd): HcControl.IR=1 → включаем OC-прерывание →
   ставим HcCommandStatus.OCR → ждём до 2 с, пока SMM отдаст владение
   (IR→0) → глушим ВСЕ источники прерываний (HcInterruptDisable) → и
   только потом HCR. В журнале печатается сырой HcControl и исход.
7. **Затирание g_io в PCI-скане UHCI**: на машине с ДВУМЯ UHCI база
   каждого найденного контроллера писалась в g_io — после привязки
   мыши на первом g_io указывал на ПОСЛЕДНИЙ найденный. Секундный свип
   считал его «нашим», пропускал, а чужие устройства на нём (флешка =
   НЕИЗВЕСТНОЕ УСТРОЙСТВО) не детектировались вовсе. Теперь база — в
   локальной переменной, g_io ставит только um_probe_controller().
8. **UHCI-свип «неизвестных»**: usb_mouse_rescan_now() выходила сразу
   при занятой мыши — новые устройства на чужих UHCI игнорировались.
   Теперь свип с edge-детектом (СМЕНА CONNECT-бита, а не «устройство
   есть»): состояние портов пишется для ВСЕХ контроллеров, действия —
   только на чужих; при занятой мыши чужой контроллер безопасно НЕ
   перечисляется (статические QH/TD одни на драйвер), а при занятых
   обоих слотах устройство честно объявляется НЕИЗВЕСТНЫМ.

### Как тестировать (методы из интернета)

Проверенные практики тестирования USB-стека самодельной ОС в QEMU —
по документации QEMU (qemu-project.gitlab.io, раздел «USB emulation»),
советам kraxel.org («USB recommendations for qemu») и обсуждениям
инъекции ввода на superuser / unix.stackexchange:

1. **Эмуляция всех четырёх типов контроллеров**: QEMU умеет UHCI
   (`-usb` / `-device piix3-usb-uhci`), OHCI (`-device pci-ohci`),
   EHCI (`-device usb-ehci`, на q35 — `ich9-usb-ehci1`), xHCI
   (`-device qemu-xhci`). Комбинируйте контроллеры и порты — как в
   тестах T1–T9b выше.
2. **Инъекция ввода через монитор**: `sendkey b` (нажатие клавиши),
   `mouse_move 25 15` (сдвиг мыши). Если в госте несколько мышей —
   сначала `info mice`, затем `mouse_set <индекс USB-мыши>` — иначе
   события уходят на PS/2.
3. **Hotplug вживую**: `device_add usb-mouse,id=mm,port=2` и
   `device_del mm` прямо на работающей системе (T8) — проверяет
   секундный опрос всех портов.
4. **Неизвестные устройства**: `usb-storage`, вторая `usb-kbd` — всё,
   что не клавиатура/мышь, обязано попасть в «НЕИЗВЕСТНОЕ УСТРОЙСТВО»
   (T7/T7b).
5. **Headless-прогон с serial-логом**: `-display none -serial
   file:qemu.log` + команды в сокет монитора — весь журнал (реестр,
   «порт, кто ты?», первые отчёты) виден в файле.
6. **Реальное железо**: фото/лог загрузки — сверьте строки
   `MOUSEHW: OHCI: HcControl=…` (владение SMM), `USBDEV: …` (реестр)
   и «первый отчёт» по каждому устройству.

# История: 0.3.2 — порты USB 2.0

## 0.3.2 — почему мышь и клавиатура не работали в портах USB 2.0

Диагноз (по коду, подтверждён логикой стека):

**Физический разъём «USB 2.0» на реальном железе обслуживает EHCI (или
xHCI), а не UHCI.** UHCI — это строго USB 1.1. Клавиатура и мышь —
low/full-speed-устройства: пока EHCI не отдаст порт компаньону
(UHCI/OHCI), устройства в этом разъёме **невидимы** для UHCI-драйверов.
В 0.3.1 это складывалось в три бага:

1. **Порядок инициализации.** `usb_mouse_init()` сканировал UHCI
   **первым** — до того, как `mouse_hw`/`ehci` выполняли handoff и
   отдавали порты 2.0 компаньонам. Мышь в порту 2.0 не находилась
   **никогда** (пересканирования не существовало).
2. **Защита «без PS/2-клавиатуры USB не трогать».** Если клавиатура тоже
   USB (PS/2 нет) и BIOS-эмуляция не отвечает на 0x60, `usb_mouse_init`
   и `ehci_init` **пропускались целиком** — оба устройства мертвы.
   Защита осталась с времён 0.3.0, когда нативных USB-драйверов
   клавиатуры ещё не было и handoff убивал BIOS-эмуляцию.
3. **EHCI гнал порт-рест в low-speed-линию.** По спецификации EHCI §4.2
   LS-устройство (Line Status = K) отдаётся компаньону **сразу и без
   реста**; реальный контроллер после такого сброса держал порт до
   таймаута. Плюс порты, уже отданные компаньону (Port Owner=1),
   опрашивались как свои.

### Что исправлено в 0.3.2 (build `0.3.2-usb20`)

* **Новый порядок инициализации** (kernel.c): `mouse_hw_init` (xHCI +
  EHCI→OHCI-handoff) → `ehci_init` (порты 2.0: HS — напрямую, FS/LS —
  компаньонам) → `usb_mouse_init` (UHCI теперь видит устройства из
  портов 2.0) → `usb_uhci_kbd_init`.
* **Снята защита «без PS/2 не трогать USB»** — на машинах с USB-клавой
  контроллеры теперь берутся всегда; откат CONFIGFLAG=0 возвращает порты
  компаньонам, если своих устройств не нашлось.
* **EHCI:** LS-устройства отдаются компаньону без ресета; порты с
  Port Owner=1 пропускаются.
* **Hotplug-перескан UHCI-мыши** (`usb_mouse_rescan` из `ps2_poll`):
  мышь, воткнутая позже (или в порт 2.0 после отдачи компаньону),
  находится автоматически, без перезагрузки.
* **Hotplug клавиатуры** (`usb_uhci_kbd.c`): выдернули/воткнули обратно —
  драйвер перепривязывается сам (раз в ~256 кадров, с дешёвым фильтром
  по PORTSC).
* **xHCI-BIOS-handoff** (`mouse_hw.c`): семафор USBLEGSUP (xECP,
  Extended Capability ID 1) снимается ДО пробинга — на современных
  платах, где «порты 2.0» висят на xHCI, MMIO больше не зависит от
  того, отдал ли BIOS контроллер.

Быстрая проверка без ISO/grub-mkrescue (multiboot ELF напрямую):

```
make run2-usb20            # q35: EHCI + 3 UHCI-компаньона, клава+мышь в «разъёмах 2.0» (порты 3-4)
make run2-uhci-kbd-mouse   # классика: оба на одном UHCI
make run2-kernel           # просто загрузиться
```

# Прошлые версии

В сборке 0.3.1 драйвер **USB HID-клавиатуры для UHCI**
(`uhci_core.c / uhci_ctl.c / uhci_kbd.c` + порт `usb_uhci_kbd.c`)
**встроен в ядро и работает**. Клавиатура на USB 1.1 (контроллер Intel
PIIX UHCI, PCI-класс `0C:03:00`) печатает в Терминал, Блокнот и проводник
как родная: boot-отчёты превращаются в сканкоды набора 1 и вливаются в
общую очередь `ps2.c`.

## Как это устроено

```
kernel.c:  usb_uhci_kbd_init()          -- после всех USB-транспортов
usb_kbd.c: usb_kbd_poll()               -- вызывается КАЖДЫЙ кадр из ps2_poll()
             \- usb_uhci_kbd_poll()      -- опрос TD прерываний
                 \- usb_kbd_parse_boot("UHCI") -- make/break -> ps2-очередь
```

Сборка: файлы драйвера входят в `KERNEL_C` (Makefile), HAL драйвера
(`hal.h`) реализован в `usb_uhci_kbd.c` поверх `io.h/string.h/PCI/serial`.

## Разделение контроллера с мышью (главная фишка 0.3.1)

Мышь (`usb_mouse.c`) и клавиатура работают **на одном UHCI-контроллере в
общем frame list**:

```
frame_list[1024] -> QH мыши (TD мыши) -> QH клавиатуры -> QH управлений
                      (горизонтальная связь usb_mouse_sched_chain)
```

Каждый переарм TD мыши (`um_arm`) сохраняет цепочку — клавиатура не
отваливается на ходу. Если мыши нет, драйвер забирает свободный
контроллер целиком (HCRESET + свой frame list). Отключение клавиатуры
от порта замечается опросом PORTSC (~1-2 сек) — драйвер отвязывается и
не мешает остальным.

## Проверено в QEMU 10.0 (build 0.3.1-uhci-kbd)

| Сценарий | Команда QEMU | Результат |
|---|---|---|
| Только клавиатура | `-usb -device usb-kbd` | перечисление, печать, Enter -> рабочий стол |
| Мышь + клавиатура, один контроллер | `-usb -device usb-mouse,port=1 -device usb-kbd,port=2` | оба живы в общем расписании |
| Hot-plug отключение | monitor: `device_del kbd0` | «клавиатура отвязана», мышь продолжает работать |

```
make run-uhci-kbd          # только клавиатура
make run-uhci-kbd-mouse    # мышь + клавиатура на одном UHCI
```

**Важно (QEMU >= 10):** при двух и более `-device usb-*` без явных
`port=` QEMU сам вставляет USB-хаб между корневым портом и устройством —
топология «за хабом» драйвером не решается, поэтому в примерах порты
заданы явно (`port=1`, `port=2`).

## Что ещё исправлено в этой сборке (найдено при интеграции)

1. **boot/boot.S — критично:** отладочная запись `'2'` в COM1 стояла
   между `xor %eax,%eax` и `rep stosl` — весь BSS заполнялся байтами
   `0x32` («мусор» во всех неинициализированных переменных: состояние
   USB-драйверов, xHCI-скан и т.д.). Маркер перенесён до установки
   регистров заполнения.
2. **kernel/usb_mouse.c:** `um_find_hid` принимал ЛЮБОЙ HID-интерфейс —
   USB-клавиатура (protocol 1) привязывалась как «мышь» и двигала курсор
   своими boot-отчётами. Теперь принимаются только интерфейсы протокола
   «мышь» (`bInterfaceProtocol == 2`).
3. **hal_pci_find_uhci (usb_uhci_kbd.c):** сравнение class-кода было
   сдвинуто на 8 бит (`>>8` против `0x0C03` вместо `>>16`), а prog-if
   читался из байта revision — UHCI-контроллер никогда не находился.
4. **bmRequestType классовых запросов:** SET_IDLE/SET_PROTOCOL/SET_REPORT
   уходили с типом `0x20` (получатель — устройство) вместо `0x21`
   (получатель — интерфейс) — устройство отвечало STALL.
5. **kernel/ps2.c:** USB-клавиатуры опрашиваются каждый кадр из
   `ps2_poll()` — раньше опрос звался только при наличии клавиш в
   очереди, а очередь наполняет сам опрос: на рабочем столе USB-клава
   «замерзала». Заодно разморожены OHCI/xHCI-клавиатуры при активной
   мыши.
6. Удалён мусор: `kernel/terminal.╤ü` (битая копия terminal.c),
   `kernel/klog_app.c` (мёртвый код вне Makefile),
   `deepseek_bash_*.sh` из корня.

## Ограничения

* Поддерживаются корневые порты UHCI (2 шт.) — устройства **за хабом**
  не перечисляются (в QEMU задавайте `port=` явно).
* Повторное подключение клавиатуры после отключения — с 0.3.2
  поддерживается (hotplug-перепривязка тем же контроллером).
* Мышь, воткнутая после загрузки, — с 0.3.2 находится пересканом
  (контроллер, которым владеет драйвер клавиатуры, не трогается —
  такую мышь нужно воткнуть до загрузки или в другой разъём).

# ЭТАП 3 — «ANYPORT»: работать всегда, на любом железе, в любом порту

Финальная стадия: устранены корневые причины «порты 2.0 мертвы на
РЕАЛЬНОМ железе при полностью зелёном QEMU» + возвращена потерянная
фича «зажал стрелку — мышь едет до отпускания» (Ctrl+J).

## Причина №1 (КРИТИЧНО): SMM-захват OHCI проверял НЕ ТЕ БИТЫ

Путь портов USB 2.0 на AMD FCH: физический порт → EHCI → компаньон
OHCI. Клавиатуры/мыши — low/full-speed → их перечисляет **OHCI**.
У OHCI-драйвера рукопожатие с SMM (BIOS USB Legacy) проверяло
`HcControl` бит **2** (PLE) вместо бита **8** (IR=0x100) и включало
прерывание OwnershipChange битом **3** (RD) вместо бита **7** (OC=0x80):

* На реальной машине (BIOS держит USB Legacy, IR=1, PLE=0) проверка
  ложно говорила «SMM не активен» → handshake **пропускался** → SMM
  оставался владельцем → после нашего HCR обработчик BIOS продолжал
  поллить контроллер и затирать наши ED/TD: `cc=5 DeviceNotResponding`,
  «control ED word0 = 0x1000», «dd8 = нули» — ровно то, что на фото.
* QEMU стартует с `HcControl=0` — эмулятор этот баг не ловил ВООБЩЕ.

Фикс: IR → бит 8, OC → бит 7 (сверено со спекой OHCI 5.1.1.3 и
Linux `drivers/usb/host/ohci.h`: `OHCI_CTRL_IR = 1<<8`,
`OHCI_INTR_OC = 1<<7`). В журнал печатается сырой `HcControl` до/после
захвата — по фото сразу видно, отдал ли SMM владение.

## Причина №2: UHCI-мышь не ставила Configure Flag

`USBCMD = RS` без `CF|MAXP`: на реальном UHCI контроллер считается
«не сконфигурированным» (SeaBIOS, Linux и наш же клавиатурный драйвер
ставят `RS|CF|MAXP`). QEMU бит CF не моделирует. Теперь ставим.

## Причина №3: игнор bMaxPacketSize0 у UHCI-мыши

Дата-стадия контрольных передач чанковалась по 64 байта, а у ВСЕХ
low-speed устройств EP0=8: TD на 18 байт завершался short-packet'ом
после первых 8, хвост дескриптора читался нулями → перечисление
срывалось. Теперь `g_ep0_mps` читается из `dd8[7]` (8/16/32/64).

## Причина №4: NAK трактовался как «успех без данных»

На реальном UHCI NAK ретайтит TD — контрольная стадия «проходила»,
не перенеся ни байта. Теперь TD переармливается и ждёт в рамках
бюджета (как uhci_core.c), NAK-шторм честно фейлит запрос.

## Возврат фичи: «зажал стрелку — мышь едет» (typematic)

В v0.3.0 с PS/2-клавиатурой стрелку можно было ЗАЖАТЬ — контроллер
PS/2 сам шлёт повторы make, курсор ехал до отпускания. У USB HID
повтора НЕТ (диф-разбор даёт одно нажатие = один шаг 8 px).

Теперь в desktop.c — программный auto-repeat: make/break стрелок
трекается (новый `KEY_BREAK`-маркер в ps2.c), и ПОКА стрелка зажата
(и активен режим Ctrl+J), курсор движется каждый кадр (15 мс):
задержка ~230 мс → шаг 4→16 px с разгоном. Работает с любой
клавиатурой: PS/2, UHCI, OHCI, xHCI, EHCI.

## Остальное из этапа 3

* **OHCI:** per-port power при PSM=1 (SetPortPower каждому порту —
  раньше только SetGlobalPower, порты компаньона с раздельным
  питанием не включались ВООБЩЕ); дебаунс подключений 100 мс
  (Linux hub.c); пауза 20 мс после перехода в USBOPERATIONAL до
  первого ресета порта; EP0 MPS из bMaxPacketSize0 (было всегда 8);
  HcRevision-лог; фикс «stale g_oi» (флешка/снимок на 2-м инстансе);
  снимок OHCI печатает ОБА инстанса AMD FCH.
* **EHCI:** ожидание BIOS-handoff до 1.5 с (было ~0.5); таймаут
  контрольного трансфера 200 мс (было 60); дебаунс CSC 50 мс;
  per-port power (PP) при подъёме CONFIGFLAG.
* **UHCI (мышь и клава):** recovery после ресета порта 50 мс (было
  5-7 мс — ниже TRSTRCY); дебаунс 100 мс; STALL на interrupt-EP
  лечится CLEAR_FEATURE(ENDPOINT_HALT); компиляторный барьер при
  воору­жении TD; выравнивание DMA-буферов (TD-буфер UHCI/OHCI не
  имеет права пересекать 4К-страницу — um_buf/um_rpt/oh_blkbuf/
  hw_rpt выровнены по размеру).
* **Ретраи GET_DESCRIPTOR(8)** ×3 с паузой 20 мс (UHCI-мышь).
* **PS/2 — постоянный fallback**: клавиатура PS/2 работает
  параллельно с USB всегда; PS/2-мышь автоматически возвращается
  при смерти USB-мыши (watchdog). «Как в Linux».

# ЭТАП 4 — «АУДИТ-ФИКС» (все 185 замечаний внешнего ревью)

Внешний аудит нашёл в коде 185 подозрительных мест (USB-стек,
загрузчик, хранилище,RTC, приложения). Каждое проверено против
исходников: часть уже была закрыта этапами 1-3, часть оказалась
неверной, РЕАЛЬНЫЕ — исправлены. Кроме того найдены и закрыты
свои ~25 багов, которых в ревью не было.

## Ключевые исправления

### Сборка и загрузчик
- **Makefile: `-fno-strict-aliasing`** (+`-fno-tree-loop-distribute-patterns`)
  — GCC -O2 мог переупорядочить обращения к DMA-структурам
  (TD/QH/qTD), переинтерпретируемым как uint32-массивы. Класс
  «QEMU зелёный — реальное железо мёртвое».
- **HDD-загрузчик: 256 → 384 КБ** (чтения 5-6, LBA 2560/2688,
  сегменты 0x5000/0x6000): ядро выросло до 250 КБ и упиралось в
  старый лимит; инсталлятор резервирует под ядро 768 секторов
  (KERNEL_SECS), запись и read-back verify — по факту размера.
- **A20-верификация** после включения через 0x92: wrap-тест
  физ 0x4 vs 0x100004, при неудаче — фолбэк через контроллер
  клавиатуры (0xD1/0xDF) и повторный тест.
- **timer.c — PIT-калиброванные задержки** (как calibrate_delay
  в Linux): все *_delay(us) драйверов раньше были циклами
  io_wait() с плавающей реальной длительностью (QEMU ~20 нс,
  реальный ПК ~1 мкс) — USB-тайминги (TRSTRCY 50 мс, recovery
  после SET_ADDRESS 2 мс, debounce 100 мс) на живом железе
  нарушались. Теперь единственный kdelay_us() калибруется по
  PIT каналу 2 (поллинг OUT2, без IRQ) при старте ядра; в
  журнале «TIMER: PIT-калибровка: N итераций / 50 мс».

### UHCI (usb.c, usb_mouse.c, usb_uhci_kbd.c, uhci_*.c)
- **DATA-toggle контрольных передач usb.c писался в read-only
  бит 19 слова ctrl_sts** (там живёт NAK-статус!), а не в token —
  все дата-пакеты Mass Storage реально уходили DATA0. Перенесён
  в TOKEN (бит 19), STATUS-стадия = DATA1.
- **PCI Command у UHCI-клавиатуры**: hal_pci_find_uhci теперь
  включает IO-space + bus-master (cmd|0x05) — на железе, где
  BIOS оставил контроллер выключенным, «найден, но молчит».
- **Фантомные порты QEMU piix3** (PORTSC несуществующих портов
  читается как 0xFF7F с битом CCS=1): бут-скан гонял reset и
  перечисление призраков (секунды таймаутов), а edge-детект
  уступки клавиатуры навсегда залипал в «уже уступали» — мышь,
  воткнутая после загрузки в соседний порт, не поднималась.
  Теперь несуществующий порт = 0xFFFF ИЛИ взведённые
  reserved-биты 13-15 (по спеке всегда 0).
- usb.c: CF|MAXP в USBCMD, ожидание снятия HCRESET, TRSTRCY
  50 мс, LS-бит в TD для low-speed, ретраи GET_DESCRIPTOR ×3,
  EP0 MPS из дескриптора, QH во все 1024 слота (был только
  слот 0 — исполнение раз в секунду при таймауте 500 мс!).
- SET_CONFIGURATION + 20 мс (noname-клавиатуры молчат).

### EHCI
- **Переарм int-qTD без полного rebuild расписания**: было
  1024 записи frame list + wbinvd на КАЖДЫЙ переарм мыши
  (~1000 р/с) — катастрофа производительности на реальном
  железе. Теперь переарм переписывает только qTD на месте;
  полный rebuild — при bind/unbind.
- STALL → CLEAR_FEATURE(ENDPOINT_HALT) + сброс дата-тоггла
  (endpoint после STALL больше не «залипает» навсегда).
- CONFIGFLAG=0 (откат портов компаньонам) + ожидание 100 мс.
- DT-бит оверлея qH сбрасывается при повторном занятии слота
  (после переподключения все отчёты нового устройства
  отклонялись из-за пережитого DATA1).
- EH_NINST 2 → 4 (платы с ASMedia), eh_data 280 → 512
  (composite-дескрипторы), PP-задержка 100 мс, сброс порта —
  таймаут 500 мс.

### xHCI/OHCI (mouse_hw.c)
- **USBLEGCTLSTS не гасился после взятия владения** — SMM-
  обработчик BIOS продолжал стрелять по контроллеру ПОСЛЕ
  нашего сброса (тот же класс «СМАЗа», что был у OHCI).
- **Слив event ring на живом контроллере без наших устройств**:
  события Port Status Change копились нечитанными, после 16
  CSC — «Event Ring Full», контроллер замолкал для будущих
  перечислений (гонка CSC при hotplug).
- DCBAA/scratchpad: выравнивание 4К и полные 64-битные записи;
  64-битный BAR в handoff-пути; g_xhci_live сбрасывается при
  неудачном ре-пробинге (poll не ходит по мёртвому MMIO).

### Хранилище и прочее
- AHCI: буфер aligned(4096), ожидание CI==0, error-recovery
  (SRST-пульс + перезапуск порта), GHC.AE перед HBA-reset,
  порты из CAP.NP+PI, LBA48 (0x25/0x35).
- ATA: таймауты по РЕАЛЬНОМУ времени (kdelay, 3 с/1 с), LBA48
  (READ/WRITE SECTORS EXT 0x24/0x34), сигнатура ATAPI 0xEB14,
  FLUSH CACHE (0xE7) после записи инсталлятора + read-back
  verify MBR и первого/последнего сектора ядра.
- RTC: век из century-регистра 0x32; notepad: защита
  utf8-хелперов от обрезанного лид-байта (курсор уходил за
  конец буфера); PCI-сканы всех драйверов — все 256 шин.

  (аксессор `uhci_kbd_bound_port(io)`); приглушённые порты ВОССТАНАВЛИВАЮТСЯ
  сбросом после пробы; контроллер с живой клавой не HCRESET-ится вовсе —
  кадры перепрограммируются, QH клавы живёт за QH мыши (общее расписание)
- **ТИПЕМАТИКА ВСЕХ КЛАВИШ «КАК В WINDOWS»** (запрос пользователя): USB-
  клавиатуры получили программный автоповтор — задержка ~500 мс, повторы
  ~30 мс (PS/2 не трогаем — у неё аппаратный). Работает во всех приложениях
  (нотепед/терминал/калькулятор), не повторяет модификаторы и Ctrl+J.
  Маркер: `KBD-TYPEMATIC: автоповтор клавиши`
- **Мгновенный детект выдёргивания мыши**: PORTSC.CCS проверяется в каждом
  64-м опросе — отключение ловится за десятки мс (раньше — только
  накоплением 2048 ошибок TD, секунды). Маркер: `CCS=0 - мышь выдернута`
- **Починен залипающий yield клавиатуры**: сценарий «выдернул мышь и БЫСТРО
  воткнул обратно» (повторное подключение приходило ДО завершения
  деактивации) оставлял флаг «уже уступали» взведённым НАВСЕГДА — мышь
  больше не поднималась. Теперь сброс по спаду CCS ИЛИ по факту «мышь
  владела слотом». T9 усилен: требует полный цикл add→del→add (2× ready)
- Адресные утечки закрыты битмапами (usb_mouse: alloc/free 1..127; EHCI:
  per-instance битмапа 1..127, free при kill/провале перечисления) —

- `bMaxPacketSize0` валидируется по скорости (LS→8, FS→8/16/32/64,
  мусор→8); bDescriptorType проверяется (device=0x01, config=0x02);
  wTotalLength клампится к реально прочитанной длине; OOB-чтение за

**EHCI (ehci.c):**
- **КРИТИЧНО: бит STS_PSS был определён как 1<<15 — а это ASS!**

## ЭТАП 5.1 — хотфикк сборки: совместимость со старыми GCC (deep-fix-v2)

Симптом на машине пользователя (Ubuntu 16.04/17.04, GCC 5/6):

```
gcc: error: unrecognized command line option '-mgeneral-regs-only'
make: *** [build/boot/boot.o] Ошибка 1
```

Причина 1: флаг `-mgeneral-regs-only` появился в GCC 7 (2017); на GCC 5/6
его не существует, а добавлялся он в CFLAGS безусловно.
Причина 2 (нашёл при воспроизведении): Makefile релиза deep-fix был
записан с 8 ПРОБЕЛАМИ вместо TAB во всех 172 строках-рецептах — GNU make
такой файл вообще не парсит («missing separator»). Пользователь дошёл до
ошибки флага, поправив табы вручную у себя.

Исправления (только Makefile, код ядра не тронут):

1. **Авто-детект флага**: перед сборкой компилируется пустой файл с
   `-mgeneral-regs-only`; если компилятор флага не знает — автоматический
   откат на `-msoft-float` (для целочисленного ядра эквивалентно: x87-кода
   в ядре нет, а SSE/MMX уже запрещены `-mno-sse/-mno-mmx/-mno-sse2`).
   В первой строке вывода make печатает выбранное:
   `GCC-режим: REGS_ONLY = -mgeneral-regs-only` (или `-msoft-float`).
   Сборка работает на GCC от 4.8 до 14+ без правки Makefile руками.
2. **TAB вместо пробелов** во всех рецептах Makefile (стиль оригинала).

Проверено в песочнице:

- GCC 14 + `-mgeneral-regs-only`: 34 файла, 0 предупреждений, 0 ошибок;
  egorov.bin 254493 / stage1 284308 / kernel 547644 / hdd_boot 1630 —
  размеры побайтово те же, что в deep-fix (код ядра не менялся)
- Эмуляция старого GCC (обёртка, отвергающая флаг точно как Ubuntu
  16.04): проба падает → `-msoft-float` → полная сборка до
  egorov.kernel — успешно
- e2e QEMU 10.0.13 после пересборки: **12/12 PASS** (T1–T12, включая
  typematic-автоповтор и hotplug add→del→add)

Быстрая проверка у себя: `make` → первая строка «GCC-режим: …»,
`grep -n REGS_ONLY Makefile` показывает блок авто-детекта.

## ЭТАП 6 — «КАРТА ПОРТОВ + AMD-оживление» (по фото №1–4 с реального ПК)

Присланные фото (8–12 гнёзд на плате, ОС видела только 5 портов,
работали только 2) дали точный диагноз — все fixes собраны в релиз
`egorov-os-0.3.0-portmap.zip`:

1. **[#412] USB-КАРТА ПОРТОВ** — запрос «программа ищет все порты и
   пишет в логе, какой это порт и какой». После подъёма ВСЕХ
   USB-контроллеров ОС печатает полную карту: каждый порт каждого
   контроллера (xHCI×2, EHCI×4, OHCI×2, UHCI по PCI-скану) с типом
   (USB2/USB3 из Supported Protocol), скоростью, занятостью (мышь/
   клава/флешка/прочее), слотом и итогом «контроллеров N, портов K,
   устройств M». Пример из QEMU: `USB-КАРТА: xHCI#1: портов 8 …
   порт 6 (USB2): High, ЗАНЯТ: МЫШЬ (слот 1) … ИТОГО: 19 портов`.
2. **[#410] Тип порта xHCI больше не врёт** — парсинг Extended
   Capabilities (Supported Protocol, ID 2): major=2 → порт USB2,
   major=3 → USB3. Раньше ВСЕ порты xHCI звались «USB 3.0» — на фото
   low-speed клавиатура «представлялась» как USB 3.0 (AMD FCH несёт
   xHCI только с USB2-линиями). Теперь «кто ты?» честный и по
   скорости устройства: Low/Full/High → «USB 2.0».
3. **[#408] OHCI: число портов NDP — полные 8 бит** RhDescriptorA[7:0]
   (спека 7.4.1; Linux читает 8 бит и клампит к 15). Была маска 0xF +
   кламп 8 → порты 9–15 были невидимы (жалоба «портов 12, видит 5»).
   Массивы ЭП-таблицы расширены до портов 1..15.
4. **[#404–#406] EHCI: «doorbell timeout» ×3 на AMD FCH** — фото
   показывало вечный цикл «перечисляю снова → GET_DESCRIPTOR не
   прошёл». Три фикса:
   - вставка control-QH БЕЗ doorbell-гейта (как Linux ehci-hcd:
     iaa_watchdog нужен только для безопасного ИЗЪЯТИЯ; HC с PARK=0
     подбирает новый QH на следующем обходе кольца);
   - eh_ensure_async(): перед звонком/вставкой подняли ASE и ДОЖДАЛИСЬ
     STS_ASS — звонок в не поднятое async-расписание не звонит НИКОГДА;
   - USBCMD пишется чтением-модификацией — полный перезапись сносил биты
     Interrupt Threshold (после HCRESET = 0x08), нулевой порог на части
     чипов ломает механизм IAA.
5. **[#409] OHCI: притушенные соседи ВОЗВРАЩАЮТСЯ** — ClearPortEnable
   при addr-0 перечислении оставлял соседний порт выключенным НАВСЕГДА
   (фото №2: «порт 4 притушён» → вечные «ДАННЫЕ НЕ ДЕСКРИПТОР» по
   соседям). Теперь oh_unquiesce_restore() ставит SetPortEnable после
   перечисления (успех ИЛИ провал).
6. **[#411] xHCI: защита от КОЛЛИЗИИ СЛОТОВ** — на фото мышь и
   клавиатура ОБЕ получили slot=1 на одном xHCI#1 (второй Enable Slot
   вернул занятый ID → слот живой мыши осиротел). Теперь коллизия
   ловится громкой строкой «СЛОТ-КОЛЛИЗИЯ … перечисление ОТМЕНЕНО» и
   живое устройство не затирается.
7. **[#403] UHCI: кэш-когерентность DMA-пула** — wbinvd до старта TD,
   в цикле опроса и перед чтением буфера (реальные ICH-платы держат
   пул в кэшируемой памяти; QEMU кэша не имеет — там безвредно).

Проверено: сборка GCC 14 — 0 предупреждений/0 ошибок; e2e QEMU
10.0.13 — **12/12 PASS** (включая T9 hotplug и T11 typematic —

USB-КАРТА:   порт 1 (USB3): пусто ... порт 5 (USB2): High, ЗАНЯТ: КЛАВИАТУРА (слот 1)

USB-КАРТА: UHCI (PCI 0:1.2): портов 2                     ← ghost-детект, до 4
USB-КАРТА: ИТОГО: контроллеров 4, портов 19, из них с работающими устройствами: 2

## ЭТАП 8 — «PEER»: единая карта ФИЗИЧЕСКИХ ГНЕЗД по модели Linux

Анализ пользователя прислал ДВА архива исходников Linux (`linux.zip` +
`drivers.part01-03.rar`, ~113 МБ). Сверка `drivers/usb/core/port.c`
(find_and_link_peer / link_peers / match_location), `drivers/usb/host/
xhci-mem.c` (xhci_setup_port_arrays / xhci_add_in_port / xhci_create_
rhub_port_array), `drivers/usb/host/xhci-pci.c` (shared_hcd) и
`drivers/usb/core/usb-acpi.c` (_PLD location) дала ТОЧНЫЙ ответ,
почему Linux «понимает» гнёзда, а прежняя карта Egorov OS — нет:

**Что делает Linux (и что НЕ делает):**
1. xHCI делит логические порты по Supported Protocol на ДВА корневых
   хаба — usb2_rhub (LS/FS/HS) и usb3_rhub (SS/SSP); каждый хаб
   нумерует свои порты ЗАНОВО (1..N). Регистрируются ДВЕ шины:
   usb2 (primary hcd) + usb3 (shared_hcd).
2. Peer-связи: корневой порт N usb2-хаба ↔ корневой порт N usb3-хаба —
   ПО ИНДЕКСУ после раздельной нумерации (find_and_link_peer, случай
   корневого хаба: hcd->shared_hcd->self.root_hub, port1 == port1).
   Это ЭВРИСТИКА по умолчанию — она верна, потому что вендоры держат
   «индекс коннектора» одинаковым в обеих половинах (USB3=порты 1-4,
   USB2=порты 5-8 → гнездо 1 = лог.порты 1+5, гнездо 2 = 2+6, …).
3. Точное физическое положение даёт ТОЛЬКО прошивка: ACPI _PLD
   (group_token<<8 | group_position) — «location». Без него Linux тоже
   НЕ знает, где гнездо на корпусе: `usb_port_probe` честно оставляет
   peer-связь «default» и НЕ выдаёт её за позицию.
4. EHCI↔компаньоны Linux НЕ сопоставляет ВООБЩЕ: FS/LS-устройство в
   гнезде EHCI маршрутизирует САМ ЧИПСЕТ (PORTSC OWNER → UHCI/OHCI),
   ОС видит устройство уже на шине usb1. Какой OHCI-порт соответствует
   какому EHCI-порту — не знает никто (в Linux это нигде не хранится).
5. Вывод для пользователя: мышь USB 2.0, воткнутая в синее гнездо
   USB 3.x, живёт на линии USB 2.0 — это НОРМА USB (SuperSpeed-линия
   просто не используется), а НЕ ошибка драйвера.

**Диагноз прежней карты (подтверждён):** она печатала раздельные списки
логических портов — «USB3: 1-4 (пусто), USB2: 5-8, мышь порт 6» — и это
ВЫГЛЯДЕЛО как путаница номеров, хотя фактически было правдой о ЛИНИЯХ.

  платах с 2+ UHCI мышь видна только на первом. (OHCI/xHCI — все 4.)

  peer-связь — эвристика по индексу протокольных списков.

## #475: «нулевая ДЛИНА ≠ нулевые БАЙТЫ ≠ нет данных»

## Архитектура (kernel/logstick.c — новый файл, 5 слоёв)

1. **Единый блочный интерфейс** поверх ТРЁХ уже существующих
   транспортов BOT/SCSI: UHCI (usb.c), OHCI (mouse_hw.c, ЭТАП 2),
   xHCI (mouse_hw.c, ЭТАП 11 — bulk-пара EP + Configure Endpoint +
   CBW→DATA→CSW по TRB-кольцам с ограниченными тайм-аутами 2–5 с
   на фазу). Интерфейс ОТДЕЛЁН от контроллеров: ёмкость (READ
   CAPACITY), чтение/запись сектора, ошибки. Приоритет выбора:
   OHCI → xHCI → UHCI.
2. **Геометрия**: MBR (4 первичных; расширенные 0x05/0x0F/0x85 —
   честный пропуск) и GPT (защитный MBR 0xEE → «EFI PART» → первые
   16 записей). Границы КАЖДОГО раздела проверяются против
   реальной ёмкости READ CAPACITY — раздел «за диском» ВЫЧЁРКИВАЕТСЯ.
3. **Выбор области записи**: единственная разрешённая цель — раздел
   FAT32 с меткой тома «LOGS» (том готовит ПОЛЬЗОВАТЕЛЬ: tools/
   mkstick.py для синтетики, форматирование в Windows для реальной
   флешки). Загрузочный MBR-раздел (0x80) и ESP GPT исключаются.
   Автоформатирования и создания разделов НЕТ. Центральный страж
   ls_wr(): запись ТОЛЬКО в [part_start, part_end) — MBR (LBA 0),
   VBR, чужие разделы, за-диск — невозможно физически.
4. **Ограниченная FAT32** (только то, что нужно EGOROV.LOG, 8.3,
   корень): поиск/создание записи, ДОПОЛНЕНИЕ файла
   (read-modify-write частичного сектора), выделение ТОЛЬКО
   свободных кластеров (FAT==0 → EOC), обновление ОБЕИХ копий FAT +
   декремент FSInfo (Windows не решит, что кластеры свободны),
   рост размера в записи каталога с датой/временем RTC. Целостность
   существующей цепочки: длина обязана сходиться с размером, иначе
   «чужие данные не перезаписываю». LFN/метки тома пропускаются.
5. **Буферизация и отказоустойчивость**: klog (RAM-кольцо 8 КБ) —
   источник; новый API klog_snapshot()/klog_oldest() корректно
   обрабатывает переполнение кольца (выгрузка со старейшего живого
   байта, байты-продолжения UTF-8 пропускаются). Дельта-выгрузка
   ls_tick() 1 Гц из usbdev_tick() с бюджетом 9 секторов на вызов

контроллеров (OHCI→xHCI→UHCI) и, не найдя на нём раздел LOGS, завершал
подготовку ОШИБКОЙ — вторая флешка не проверялась вовсе.

**Стало (kernel/logstick.c):** `ls_blk_enumerate()` перечисляет ВСЕ
видимые накопители (до трёх — по одному на транспорт), КАЖДОМУ печатает
модель (SCSI INQUIRY) и ёмкость (READ CAPACITY, секторы и МБ), затем
КАЖДЫЙ пробуется: запись выбирается на тот накопитель, где реально
найден раздел LOGS. Перед первой записью печатается ПОДТВЕРЖДЕНИЕ
выбора: «ВЫБРАН накопитель 2/2: UHCI '…', N секторов - НА НЁМ раздел
LOGS, запись ТОЛЬКО в этот раздел». Накопитель без раздела LOGS
пропускается честной строкой «на этом носителе раздела LOGS нет -
проверяю следующий». Тест **L12** (две флешки: OHCI без LOGS + UHCI с
LOGS) проверяет и переход ко второй, и что на первой файла НЕТ.

**Честное ограничение (не устранено, задокументировано):** каждый
транспорт держит ОДИН MSD (usb.c — один `usb_drive`, mouse_hw.c —
один `g_oh_msd`/`g_xm_slot`). Две флешки за ОДНИМ контроллером одного
типа не различаются — увидена будет одна. Для гарантированного выбора
второй флешки подключайте её к контроллеру другого типа (например,
загрузочная — USB 3.0/xHCI, журнальная — USB 2.0/OHCI-компаньон) или
к свободному UHCI. Мульти-MSD на транспорт — отдельная задача
(перечисление нескольких адресов), сознательно НЕ делалась (запрет
«не переписывать USB-стек»).

## Проблема 2: целостность файла при ошибке записи (ls_dir_update)

**Было:** в `ls_append()` результат `ls_dir_update()` НЕ проверялся:
данные в кластеры записаны, а размер файла в каталоге — нет; ядро
считало выгрузку успешной, хотя том не отражал её полностью.

**Стало:**
* `ls_dir_update()` проверяется ВСЕГДА (и для первого кластера, и для
  роста размера). При сбое: `g_meta_fail`, честная строка «данные
  записаны в кластеры, но запись каталога (размер файла) НЕ обновилась:
  на томе файл короче на N байт», выгрузка ОСТАНАВЛИВАЕТСЯ (писать
  вслепую поверх несогласованного размера нельзя), `ls_status()` =
  «каталог не обновлён - выгрузка остановлена».
* В ИТОГе печатается точное расхождение: «размер в каталоге X байт, в
  кластеры записано Y байт - несоответствие … проверь том (chkdsk)».
* Транспортная ошибка чтения FAT/каталога больше НЕ маскируется под
  «нет свободных кластеров» (`g_fat_scan_err`): выдернутая флешка
  получает честную причину «FAT не читается (транспортная ошибка)».
* Извлечение во время записи покрыто тестом **L9** (device_del).

## Проблема 3: журнал с самого старта (кольцо 8 КБ затирало начало)

**Было:** до обнаружения флешки журнал жил только в кольце 8 КБ;
ранние сообщения перезаписывались, выгрузка начиналась с
`klog_oldest()` — «весь журнал с момента запуска» не выполнялось,
потери не назывались.

**Стало (kernel.c + kernel/logstick.c):**
* **Ранний ЛИНЕЙНЫЙ буфер 128 КБ** (`klog_early_buf`): первые байты
  журнала пишутся без затирания и доживают до готовности носителя.
  Размер — cmdline `logearly=N` КБ (по умолчанию 128, тест L13 — 1).
* **Кольцо 8 КБ → 64 КБ** (эффективный размер — cmdline `logring=N`
  КБ, 8..64, по умолчанию 64): мгновенные взрывы диагностики (СНИМКи
  ~20 КБ) больше не затирают журнал между тиками выгрузки (замерено в
  L12 до исправления: терялось 19 677 байт за один взрыв).
* Выгрузка ДВУХФАЗНАЯ: ранний буфер [0..E) → кольцо [max(E,oldest)..);
  дыра между ними (буферы переполнены) — ЧЕСТНЫЙ МАРКЕР в файле
  «=== LOGS: ДЫРА: потеряно N байт журнала … ===» + число в ИТОГе.
* Переполнение кольца ПОСЛЕ старта выгрузки — аналогичный маркер с
  числом потерянных байт (плюс пропуск байтов-продолжений UTF-8 на
  рваной границе, чтобы файл оставался валидным UTF-8).
* ИТОГ честен: «журнал ПОЛНЫЙ с первого байта загрузки» — только если
  буферы целы И доставка прошла (stage 1); при потере — «ПОТЕРЯНО N
  байт … - журнал НЕ полный»; при обрезке лимитом/отказе носителя —
  «буферы держат журнал с первого байта, но ХВОСТ в файл НЕ попал».
* Заголовок сессии в файле содержит строку покрытия: «журнал: ПОЛНЫЙ
  с первого байта, ранний буфер N байт» либо «журнал: ПОТЕРЯНО N байт
  старта (ранний буфер M КБ переполнен)».
* Тесты: **L1–L3** требуют в файле САМЫЙ ПЕРВЫЙ баннер ядра
  («=== Egorov OS … kernel_main ===») и отсутствие маркеров ДЫРА;
  **L13** (`logearly=1 logring=8`) требует маркер ДЫРЫ в файле,
  «ПОТЕРЯНО N байт» в ИТОГе и ОТСУТСТВИЕ заявления о полноте.

## Проверка (Сборка 4, QEMU 10.0.13)

* Сборка: GCC `-mgeneral-regs-only`, **0 предупреждений / 0 ошибок**

  кольца в .bss — NOBITS, в файл образа не попадает).
* **e2e_logs.py: 14/14 PASS** — L1–L3 (UHCI/OHCI/xHCI: файл содержит

## Честные НЕпроверенные сценарии (Сборка 4, дополнение к списку Сборки 3)

1. **Две РЕАЛЬНЫЕ флешки на РЕАЛЬНОМ железе** (разные контроллеры):
   QEMU-модель L12 подтверждает логику перебора, но VID/PID, тайминги
   и порядок перечисления живого железа не гонялись.
2. **Вторая флешка за тем же контроллером того же типа**: НЕ
   поддержано (один MSD на транспорт — см. Проблему 1); сообщение об
   этом честно напечатано в кандидатах.
3. **Сбой записи каталога на живом железе** (данные записались, размер
   нет): код покрыт (g_meta_fail, точные числа), QEMU readonly/device_del
   дают только полный отказ записи; частичный отказ не моделировался.
4. **Превышение 128 КБ раннего буфера + 64 КБ кольца на реальной
   загрузке**: маркер потери и подсчёт покрыты тестом L13 (урезанные
   буферы), но реального сеанса с >192 КБ журнала до готовности
   носителя не было.
5. **Чтение EGOROV.LOG в Windows** после Сборки 4: структура не
   менялась (Сборка 3 формат); проверялось только хост-читалкой теста.
